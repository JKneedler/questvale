# Retheme Color

Changes one of a **named theme's** four core colors (Primary, Secondary, Surface, Surface Container) everywhere it's expressed — in that theme's `AppTheme` entry and in that theme's own per-theme PNG folder — so the user can freely retune a palette without hunting down every place a color is baked in.

**Always requires an explicit theme name up front** (e.g. "charcoal-gold") — never infer "the active theme". Since Questvale added a multi-theme system (2026-07), which theme is currently active is just a value on the `Character` record (`themeId` column, read via `ThemeCubit`), not something this skill should try to introspect — the user might want to retune a theme they aren't even currently using. If the user says "retune the theme" without naming one, ask which theme before doing anything else.

**Surface Container** was promoted to this skill's scope in 2026-07 — coincidentally equal to Metal Corner's Main (`#cbcbcb`) in the original `charcoal-gold` theme, but meant to be retuned fully independently of Metal Corner (which isn't part of any theme — Metal Corner/silver assets are shared and theme-independent). Treat any future coincidental match with Metal Corner the same as step 3's cross-field check, not as a reason to couple them.

**Backing script:** `.claude/skills/retheme-color/retheme_color.py` (Pillow-based). Two modes:
- `derive --old-main --old-light --old-dark --new-main` (hex, no `#`) — prints suggested new Light/Dark Accent shades via an HSL lightness/saturation offset from the old Main, applied to the new Main's hue. Use this when the user gives only a new Main color and hasn't specified accent shades themselves. Note this offset method can produce tinted, non-neutral results when shifting between a saturated and a desaturated/neutral hue (seen once already, shifting the original warm brown palette to `charcoal-gold`'s cooler grays) — if the suggestion looks off, offer a hand-computed lightness-stepped alternative (same hue/saturation as the new Main, just lighter/darker) instead, and always confirm with the user before finalizing either way.
- `apply --pair OLDHEX:NEWHEX [--pair ...] (--dir DIR | --files a.png,b.png,...) [--dry-run] [--include-icons]` — substitutes exact RGB pixel values, skipping transparent (`0,0,0,0`) and drop-shadow (`0,0,0,52`) pixels. `--dir` recursively scans (excluding `images/ui/icons/` by default); `--files` takes an explicit comma-separated list — **always use `--files` scoped to the named theme's own folder**, never `--dir images/ui` (that would also scan every *other* theme's folder and the shared, theme-independent assets). Always dry-run first and inspect the per-file pixel-count summary before writing for real.

Border is intentionally **not** part of this skill's scope — it's a fixed universal `#000000` across every theme, not stored per-theme at all, specifically so a Primary/Secondary/Surface/Surface Container change never ripples into the border ring. Don't reintroduce that coupling; if the user wants Border to vary by theme, that's a separate, explicit decision (see vault `02_Design_System/Theming.md`).

**Pressed-state button variants** (added 2026-07, alongside `QvButton`'s tap animation): each of the 4 roles this skill covers has a `button-<role>-pressed.png` sibling in the same per-theme folder, built by swapping that button's Light and Dark Accent pixel values (see `create-theme`'s SKILL.md for how it's originally generated). Retuning a role's Main/Light/Dark here must include that role's `-pressed.png` file in the same substitution pass — it uses the exact same `--pair` list as the un-pressed file. Because the pressed file already has Light and Dark swapped at the pixel level, applying an identical old→new pair substitution to both files automatically preserves the swap relationship in the retuned result (verified this holds — no special-cased pair ordering needed). Skipping the pressed file leaves it retuned to a color that no longer belongs to any confirmed value, which won't throw but will look wrong the moment that button is pressed.

## Steps

1. **Confirm the theme name, the role, and the new Main hex.** The theme must already exist in `lib/helpers/constants.dart`'s `APP_THEMES` map — if the name given doesn't match an existing key, stop and ask (don't create a new theme here; that's `create-theme`'s job). One of Primary/Secondary/Surface/Surface Container, plus the new Main color. If the user hasn't given explicit new Light/Dark Accent values, run `derive` with the role's current Main/Light/Dark and the new Main, and present the suggested accents for confirmation before proceeding — don't just apply them silently.

2. **Read that theme's current values fresh from `lib/helpers/constants.dart`'s `APP_THEMES['<themeId>']`** (not the vault, not memory — code is the runtime source of truth) and cross-check against the vault's `02_Design_System/Color Palette.md` row for that theme/role. If they disagree, stop and ask which is correct rather than picking one.

3. **Cross-field duplication check.** `AppTheme.colorScheme` derives `onPrimary`/`onSecondary`/`onSurface` from other fields on the *same* `AppTheme` (`onPrimary` = that theme's `surfaceMain`, `onSecondary` = that theme's `primaryMain`, `onSurface` = that theme's `primaryLight` — see the getter in `constants.dart`). Check whether the role being changed feeds one of those derived fields — if so, the derived field updates automatically as a consequence (that's intentional, matches the established cross-role contrast pattern), but call it out to the user rather than letting it pass silently. Separately, check whether any *other* `AppTheme` field on this same theme happens to exactly equal one of the *old* hex values about to change, coincidentally, for a reason unrelated to the derivation above — report and confirm before touching those too.

4. **Grep `lib/` for stray hardcoded color literals** matching the old hex(es) — `Color(0x...)`/`Color.fromARGB(...)` outside of `constants.dart`'s `AppTheme` definitions. As of 2026-07 there are none (the last known instance, `PRIMARY_DARK_ACCENT_COLOR`, was removed entirely — Primary's Dark Accent is read from `AppTheme.primaryDark` via `ThemeCubit` now), but re-check live every run since this can drift again as new code is added.

5. **Dry-run the asset pass**, scoped strictly to the named theme's own files: `retheme_color.py apply --pair OLDMAIN:NEWMAIN --pair OLDLIGHT:NEWLIGHT --pair OLDDARK:NEWDARK --files images/ui/buttons/<themeId>/button-<role>.png,images/ui/buttons/<themeId>/button-<role>-pressed.png,images/ui/borders/<themeId>/border-<role>-mini.png,...` (build the exact file list from that role's known assets — for Primary also include `border-primary.png` and the hybrid `border-primary-metal-edge.png`, which mixes Primary with Metal Corner's own untouched colors; for Surface Container also include `images/ui/buttons/<themeId>/button-surface-container-no-bottom.png` (used by `QvBackground`, one of several no-cap-edge `QvBackground` variants that all live alongside the rest of the button family in `buttons/` despite the class's own name — none have a pressed-state sibling, since `QvBackground` has no press interaction); for Surface also include that same family's other three: `button-surface-no-bottom.png`, `button-surface-no-top.png`, `button-surface-no-top-no-bottom.png` — and always include that role's `button-<role>-pressed.png` sibling with the exact same `--pair` list, never a separate swapped-order one). Show the user the per-file changed-pixel-count summary. A file expected to use this color family that comes back with 0 changed pixels is a red flag — investigate before proceeding. Confirm with the user, then re-run without `--dry-run`.

**A note on `button-<role>-no-top.png` specifically**: unlike every other asset in this family, it is *not* just `button-<role>.png` with pixels swapped — it was built by flattening `button-<role>.png`'s own top cap into its flat body pattern, keeping that source's real (correctly-shaded, raised) bottom cap untouched. A plain pixel-substitution pass still recolors it correctly (same three colors, same positions), but if it's ever regenerated from scratch for a new role, regenerate it the same way — flatten `button-<role>.png`'s top rows into its own row-12 pattern — never by vertically flipping `button-<role>-no-bottom.png`. That was tried once: flipping carries the Light highlight from the top cap down to the bottom edge, which reads as inset rather than raised, since a raised cap's shading isn't just mirror-symmetric (top cap = Light highlight; bottom cap = Dark accent + a drop shadow beneath it — see `button-surface.png` itself).

6. **Update `constants.dart`'s `APP_THEMES['<themeId>']` entry** — the role's Main/Light/Dark fields (writing the exact confirmed values used in the pixel substitution, not just the Main that was asked for) plus any confirmed cross-field duplicates/derived fields from step 3, and any confirmed stray literals from step 4.

7. **Update the vault**, in the vault's own repo (never this repo's git history — same rule `capture-decision` follows):
   - `02_Design_System/Color Palette.md`'s row for this theme/role (Light Accent/Main/Dark Accent hex columns) — note the theme name, since the vault may eventually document more than one theme.
   - `02_Design_System/Theming.md`'s "Colors → Code" table and, if the change affects anything described in "Asset Color Roles", that section too.
   - Commit with a message describing what changed and which theme (e.g. "Retune charcoal-gold's Primary from gold to teal"), same convention as `capture-decision`.

8. **Print a final summary**: theme name, Dart file(s) touched, PNG(s) touched with pixel counts, vault commit hash. Remind the user to run `flutter analyze` and eyeball the result in the simulator — a missed asset or wrong hex assumption shows up as a visual mismatch, not a compile error. If the retuned theme happens to be the character's currently active theme, the change is picked up automatically on next `ThemeCubit` rebuild (hot-reload/restart) — no special handling needed.

## Guardrails

- Never proceed without an explicit, existing theme name — ask rather than assume "the active theme" or default to `charcoal-gold`.
- Never touch transparent (`0,0,0,0`) or drop-shadow (`0,0,0,52`) pixels — `retheme_color.py` already skips these, don't work around it.
- Never scan or edit `images/ui/icons/` — out of scope for this skill.
- Never use `--dir` for the asset pass — always `--files` scoped to exactly the named theme's own folder, so other themes and shared/theme-independent assets (rarity, silver, skill borders, health border, checkboxes, nav, icons) are never touched.
- Never retune a role's `button-<role>.png` without also including its `button-<role>-pressed.png` sibling in the same substitution pass — leaving it out silently desyncs the pressed texture from the retuned palette.
- Never touch Border — it's a fixed `#000000` independent of every theme; don't reintroduce the coupling that was deliberately removed.
- Never cascade a change into another `AppTheme` field, another theme entirely, or a stray literal without explicit confirmation, even on an exact hex match — coincidence isn't intent.
- Always dry-run the PNG pass and show the summary before writing for real.
- Vault commits stay in the vault's own repo — never commit vault-targeted changes into this repo's git history.
- If a file expected to contain the old color comes back with zero substituted pixels during the real (non-dry-run) apply, stop and investigate rather than treating it as done — a silent no-op usually means a wrong hex assumption, not a "nothing to do here."
